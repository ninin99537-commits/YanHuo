# 彼方 · NPC幕后生命状态系统 (Elsewhere)

每次更新项目同步更新此说明

一个运行在酒馆助手 (Tavern Helper) 中的脚本项目。根据《Elsewhere / 彼方 - NPC幕后生命状态系统设计初稿》实现: **让角色在离开玩家视野后, 依然保持"正在生活"的状态**。

玩家看到的是角色人生中的一个镜头, 彼方负责维护镜头之外的状态: 不记录 NPC 每天发生了什么、不生成大量后台剧情、不模拟完整人生, 只记录 NPC 当前最重要的幕后状态。

## 工作原理

每次 AI 完成一次正文回复后:

```
正文生成完成
      ↓
彼方更新幕后NPC状态 (使用独立的 OpenAI 兼容 API)
      ↓
更新每个不在当前场景中的 NPC 状态
      ↓
保存最新状态 (写入当前聊天的聊天变量)
```

- **哪些 NPC 会被更新**: 由 AI 从最近几条正文回复中**自动识别重要 NPC**(排除路人、店员等功能性 NPC), 对**所有已追踪 NPC 与实际出现的新重要 NPC** 一律更新完整状态卡(不再区分在场/不在场, NPC 出现在正文中时字段自然反映其在场景中的状态); **防全知信息边界保留**: 未在正文中出现的 NPC 不知道正文里发生的任何事, 其字段只写它自己生活中的内容。监控名单也可以手动维护, 名单随当前聊天保存, 新聊天默认从空开始。
- **NPC 状态卡字段**: 当前在做、当前状态、位置、身份锚点、近期关键事件、接下来想做、当前目标、心里惦记、未完成事项、生活状态、秘密想法、隐藏目标。
- **更新原则**: 不强行变化、不制造大剧情、保持角色一致性、只记录必要信息、只记录重要 NPC; 检测到"几天后 / 几个月后 / 一年后"等时间跳跃时只反映跳跃后的当前状态; **时间的流逝（几十分钟/几小时/睡了一觉/一天/几天）也会推进 NPC 状态**——例如主角睡了一觉醒来是清晨，前一天晚上还在上班的 NPC 应处于清晨的合理状态，而不是停留在昨天场所。
- **一致性铁律**(AI 无记忆 + 楼层覆盖的解决方案): 旧卡里写下的具体物品名/承诺内容/约定时间地点**绝不可泛化**(玩偶就是玩偶, 不得改成"礼物"); 「近期关键事件」由代码按 FIFO 维护最多 3 条, 跨楼层短期记忆。

## 扩展字段说明

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| 身份锚点 | 字符串 | 一句话概括 NPC 的独立身份与日常(职业/家庭/作息), 抗"围绕主角转"; 新建必填, 之后只在人设被改写时更新 |
| 近期关键事件 | 字符串 | 该 NPC 近期亲历的关键事件(最多 3 条, 代码按 FIFO 淘汰); 跨楼层短期记忆 |
| 未完成事项 | 事务台账(数组) | 答应过、定下要做的具体事——**不再是一句话, 而是一本只增不改的账**: 每项是 `{编号, 时间, 内容, 状态, 结果}`, 编号(T1/T2…)由代码分配, **内容写下即冻结**(含具体物品/人名/地点, 不得泛化), 之后只能改它的**状态**(只有 `进行中`/`已完成`/`已作废` 三个值)与结果——要改内容就作废旧条、另开新条; 每个 NPC 最多 8 条, 超额先淘汰最旧的已办, **`进行中` 永不淘汰**; 旧数据里的整句字符串会在读取时自动迁移成一条 `进行中`(内容一字不改) |
| 秘密想法 | 字符串 | (扩展) 不会轻易透露的真实想法, 不注入主AI提示词 |
| 隐藏目标 | (扩展) 藏在心底、不会明说的目标, 不注入主AI提示词 |
| 位置 | 字符串 | 当前所在位置 |

## 恋爱子系统（标记即开关，没有全局设置项）

在 NPC 详情页点「标记恋爱对象」即开启：此后每一轮幕后更新，该 NPC 都会按 AI 报的**恋爱事件**折算两条轴。**没有标记任何 NPC 时，提示词与合并逻辑与从前逐字节相同**（这是本子系统的验收红线：不标记 = 零成本、零回归）。

**AI 只报事实，代码算数值**：AI 只返回 `恋爱事件`（`{轴, 类型, 强度, 依据}`），**绝不允许输出任何数字**；好感值/情欲值/阶段/地板/上限全部由代码产生（`恋爱规则.ts`，纯函数）。

| 字段 | 类型 | 说明 |
| ---- | ---- | ---- |
| 恋爱对象 | 字符串 | `是` = 已标记。**标记即开关**，取消标记 = 清空该字段；没有全局设置项 |
| 情感倾向 | 字符串 | 枚举 `内敛/常规/外放/慢热/病娇`，各带 (敏感度, 粘性) 两个系数。内敛 0.7/0.9、常规 1.0/1.0、外放 1.4/1.0、慢热 0.6/0.6、病娇 1.6/0.2 |
| 好感值 | 字符串 | 0–100，1 位小数。**存量**，只受事件影响，不自然衰减；首次结算前为**空**（未结算，不等于 0） |
| 情欲值 | 字符串 | 0–100，1 位小数。**状态量**，会被满足与时间回落；首次结算前为**空**（未结算，不等于 0） |
| 好感阶段 | 字符串 | 陌生 0-15 / 认识 16-30 / 熟悉 31-50 / 朋友 51-70 / 暧昧 71-85 / 恋人 86-95 / 挚爱 96-100 |
| 情欲阶段 | 字符串 | 无感 0-20 / 有性趣 21-45 / 想要 46-75 / 饥渴 76-100 |
| 名分 | 字符串 | `无/恋人/未婚妻/炮友`，由名分事件驱动（必附原文依据），玩家可直接改；未说定前为**空**，清空即清空（不会自动补回 `无`） |
| 恋爱标签 | 字符串 | 闭合词表（青梅竹马/主仆/单恋/冷战/心结/猜忌/占有欲/依赖/口是心非/敌意/恐惧/厌恶），最多 5 个，词表外的词丢弃 |
| 恋爱态度 | 字符串 | 一句话，只写**外在可观察的倾向**（不写内心独白），随注入条目提供给主 AI |
| 恋爱动向 | 字符串 | 最近一轮的因果一行：`好感+3(交心) / 情欲−4(时间回落2天) · 2026-08-15`；时间回落也记成因与天数 |
| 恋爱基准日期 | 字符串(隐藏) | 上一轮结算的剧情日期，供时间回落算天数；只前进不倒退，剧情时间缺失时跳过回落且不更新 |
| 恋爱开局 | 字符串 | 开局标记（`是`/空）。**只有接受过一次开局才会写**；清空它（且 `恋爱动向` 也为空）即重新开局——两道闸同开才会再问一次 |

**冷启动 / 开局**：人设里写着「青梅竹马 / 未婚妻 / 已在一起多年」的 NPC，标记后如果不做任何事，第一轮会结算成 `好感 0 / 陌生`——模型被禁止报数字，而"既成关系"也不是本轮正文，靠自己又爬不上去（单轮上限 +8，从 0 到恋人档至少 11 轮）。所以「起点」做成**第五样惰性补齐**：AI 在 `恋爱事件` 数组里**额外加一条** `轴: "开局"` 的元素，报**阶段名**（`好感`/`情欲`/`名分` 三个键都可省，`依据` 必填、可以来自人设而非正文），代码按**档下界**落值（恋人 → 86、有性趣 → 21；取档下界而非中点：既保守，又不与 ±2 滞回打架）。

- **两道闸同时成立才接受**：卡上 `恋爱开局 ≠ 是`（还没开过）且 `恋爱动向` 为空（还没有过任何变化）。第二道是**防迟到乱开**——跑了十几轮的 NPC 不会被一个错报的开局直接跳到恋人档。
- **开局是基线不是增量**：不吃单轮上限（`挚爱` 直接落 96）；同轮既有开局又有事件时**先落基线、再应用事件**。
- **只填缺省、绝不覆盖**（玩家手改优先）；同轮里 `名分` 事件压过开局名分（正文比回溯权威）。
- 接受后写 `恋爱开局 = 是`，并在 `恋爱动向` 里留一行 `好感开局 86(人设：…)`（开局行排在增量行之前）；**没报开局就什么都不写**，窗口保持开着，下一轮还能开。
- **空轮不落库（§3.9 第 4.5 条）**：数值状态类字段加了「**有值才写**」的闸——`该轴有值 = 卡上该字段非空 ∥ 本轮开局填了该轴 ∥ 本轮该轴有事件`（事件看**折算命中过没有**，不看净额：`+3` 与 `−3` 同轮相抵、净额 0，照样落值）。`名分` **没有伴生字段，所以闸更紧**：只在**真的变了**或本轮开局填了它时才写（卡上已有的名分不会每轮空转写回；玩家清空后也不会被补成 `无`）。`情感倾向` / `恋爱基准日期` 是配置与锚点，**照旧无条件惰性补齐**。所以标记后、第一次产生数据之前，两条轴在卡上是**空**而不是 `0 / 陌生`——「已知为 0」与「还不知道」从此可区分，也是「漏报不锁死」成立的前提（否则漏报那轮先把 `好感值` 落成 `'0'`，下一轮开局就填不进去了）。为什么按轴判而不是「本轮无事就全不写」：后者会让「手改 `好感值` 后阶段自动跟上」失效（那一轮正好没事件时阶段就不重算）。

**规则要点**：①阶段带 ±2 滞回（`值 ≥ 上界+2` 升档 / `值 ≤ 下界−2` 降档，可跳档），且**卡上有值就每轮重算**（手改数值后阶段自动跟上；卡上还没值又没事件时**不落库**，见「空轮不落库」）；②**先按方向分桶、只夹涨桶、再相抵**（好感 +8 / 情欲 +20，落桶不设限）——若先净额相抵再夹，同轮的落事件会掩盖超上限的涨（涨 +24 与落 −10 会被当成 +14 而完全不夹），一条「性行为(大)」也仍是真的 −35；③系数怎么乘：好感涨/落与情欲涨 × 敏感度，**情欲落（满足回落 + 时间回落）只 × 粘性、不乘敏感度**（否则"外放"会变成"性爱之后冷却得更快"）——病娇的「性行为(大)」= −35 × 0.2 = **−7**；④情欲地板（熟悉 10/朋友 15/暧昧 30/恋人 45/挚爱 60）按**结算后**的好感阶段取，**只截断回落、不抬升**：`实际回落 = min(|落桶|, max(0, 涨后情欲 − 地板))`，所以"深爱但清心寡欲"能存在、手改的值不会被凭空抬高；⑤时间回落 = 每跨 1 个剧情日 −2 × 粘性；⑥**「依据」是入场券**：名分事件缺依据（空串/缺键/全空白）→ **整条拒绝**（名分不变、不写动向，另打一条 warn）；数值事件缺依据 → 仍折算，只 warn（数值是渐变量，全丢弃会让数值完全不涨）。依据一律作为原文附进 `恋爱动向`，**没有 `依据 || 类型` 这类兜底**；⑦**`恋爱标签` 是闭合词表，两条写入路径都过同一把尺子**：AI 路径（`mergeCard` 之后归一化）与玩家路径（`合并草稿`）都调 `校验标签`；**「归一化后为空」不等于「想清空」**——本轮报的词一个都不在词表里（AI 报错）→ 保留旧值，玩家清空输入框（空串）→ 删字段；⑧`恋爱动向` 记**实际**变化量（被地板截断后的值）与成因，**本轮全零就不写、保留原值**。

## 安装

1. 运行 `pnpm build` (或 `pnpm watch` 开发) 生成 `dist/彼方_NPC幕后生命状态系统/index.js`。
2. 在酒馆助手中新建脚本, 将打包后的 `index.js` 内容填入并启用。
3. 也可以把脚本文件夹放进 `src/彼方_NPC幕后生命状态系统` 后使用本项目的实时监听 / 热重载功能。

| **YanHuo** `ninin99537-commits/YanHuo` | 烟火的官方发布仓（投影仓） | 烟火全量 + 共用 + **彼方全量** | 烟火 |

import 'https://cdn.jsdelivr.net/gh/ninin99537-commits/BiFang@master/dist/彼方_NPC幕后生命状态系统/index.js';

### ⚠️ 为什么不能直接 `git push`

工作区的 `git remote -v` **只有一个 `origin`，它指向 YanHuo**。所以在工作区里敲 `git push origin master`，既不是发布彼方、也不是发布烟火。三个原因：

1. **投影仓不是工作区的镜像。** 工作区 `src/` 下有 8 个插件，投影仓只装 3 个。直接推会把剧情导演 / 正文美化 / 直播弹幕 / 自定义状态栏一并带过去。
2. **两者历史已经分叉。** 工作区与 `origin/master` 各有独有提交（实测 `git rev-list --left-right --count HEAD...origin/master` = `223 20`），普通 push 会被拒。
3. **`dist/` 的跟踪状态相反。** 工作区 `.gitignore` 里写着 `dist`（不跟踪），而两个投影仓都**跟踪** `dist/`——jsdelivr 导入的正是它。

所以发布 = **投影**：把文件复制到目标仓的检出里，在那里重新提交、再推。**不是** push 工作区。

### 投影怎么做（照抄）

1. 把 BiFang 克隆到工作区**之外**（或工作区内一个不被跟踪的目录，如 `.work/`）：

   ```bash
   git clone https://github.com/ninin99537-commits/BiFang.git <工作区外>/BiFang-recon
   ```

2. `pnpm build`，确认 `dist/彼方_NPC幕后生命状态系统/index.js`（+ `.js.map`）重新生成、含你的改动。

3. 从工作区**复制**下列内容到检出：

   | 复制什么 | 说明 |
   | ---- | ---- |
   | `src/彼方_NPC幕后生命状态系统/**` | 本插件全部源码 |
   | `src/共用/**` | 两家共用（4 个文件），**有改动才需要** |
   | `tests/**` | 公共骨架 4 个（`build.mjs` / `run.mjs` / `platform-usage.mjs` / `tag-filter.test.ts`）+ 本插件全部 `*.test.ts` |
   | `dist/彼方_NPC幕后生命状态系统/index.js` + `.js.map` | 第 2 步的产物 |
   | `docs/仓库首页-彼方.md` | **改名为 `README.md`**（投影仓的首页就是它） |
   | `docs/彼方-*.md` / `.html` | 本插件的设计文档 |

4. 在检出里提交并推送：

   ```bash
   git -C <检出> add -A
   git -C <检出> commit -m "..."
   git -C <检出> push origin master
   ```

### 陷阱清单

- **`dist` 必须一起带上。** 工作区不跟踪它、投影仓跟踪它。漏了会让 jsdelivr 继续发旧产物（`[bot] bundle` 能兜底重建，但中间态期间线上是旧的）。
- **别把其他插件带过去。** 剧情导演 / 正文美化 / 直播弹幕 / 自定义状态栏不属于这个投影。
- **`.github/workflows/` 只放 `bundle.yaml`。** 工作区里另有 `bump_deps.yaml` / `sync_template.yaml`，那是模板上游维护用的，两个投影仓都没有它们。
- **`tests/platform-usage.mjs` 已兼容"缺项目"的投影仓。** 它扫的项目目录不存在就跳过（`statSync(..., { throwIfNoEntry: false })`），不再抛 `ENOENT`。所以投影仓里 `pnpm test` 最后那道「平台直连检查」不会因为它变红；**它红了就是真的出现了 `host.ts` 之外的平台直连**——那才是它要抓的东西。
- **新克隆没有 git identity：`commit` 会失败，而 `push` 会撒谎。** 投影检出是全新克隆，本地与全局都没配 `user.name` / `user.email` 时，`git commit` 直接 `exit 128`（`Author identity unknown`）；**紧接着的 `git push` 会报 `Everything up-to-date`** —— 看起来像推成功了，其实根本没产生提交（工作树还是脏的）。先设本地身份（`git -C <检出> config user.name "..."` 与 `user.email "..."`，**只写本地、别加 `--global`**）再提交。
- **判断推没推上去，看 `rev-parse` / `ls-remote`，不看 `push` 的输出。** `Everything up-to-date`、`Already up to date.` 都可能出现在"什么都没发生"的场景里。推完用 `git -C <检出> rev-parse HEAD` 与 `git -C <检出> ls-remote origin master` 对一次，两边一致、且 `status --porcelain` 为空，才算真的落地。
- **jsdelivr 有缓存。** `@master` 是非版本号引用，缓存较久；`[bot] bundle` 会自动打版本 tag，把刷新压到 12 小时内。要立刻验证，就用 **commit hash 或 tag** 直接 import。
- **推完要真机验证。** jsdelivr 刷新前，酒馆里跑的还是旧产物。

> 🤖 两个投影仓都有 `[bot] bundle` 工作流：推源后机器人会自动 `rm -rf dist && pnpm install && pnpm build` 并补一个提交，所以即使偶尔漏提交 dist 也会被兜底重建；但它只重建**仓内存在 `index.ts` 的插件**，而产物由 `webpack.config.ts:54` 的 `globSync('{示例,src}/**/index.{ts,tsx,js,jsx}')` 决定——这就是为什么 YanHuo 的 `dist/` 有两份、BiFang 只有彼方一份。
> ⚠️ **本机构建与 CI 构建不可能逐字节相同**——webpack 的模块 ID 由模块绝对路径派生，而两台机器的检出路径不同（实测同一段代码：本机 `777(e,n,t)`、CI `463(e,n,t)`）。所以推完源码后机器人**几乎总会**再补一个提交，这是正常现象，不是出错；也不必试图靠"提交一份完全一致的 dist"来避免它。
> 推送被拒（non-fast-forward）时，多半是机器人刚补过一行：`git rebase origin/master` 后再推。

> ⚠️ 同名仓库 `YanHuo` 里也有彼方全量源码（历史沿革，它的 `dist/` 因此也会构建出彼方产物）——但那里是烟火的主场，彼方的「官方发布仓库」是 `BiFang`，上传彼方改动以 BiFang 为准，YanHuo 里那份副本不保证同步。

## 配置

在酒馆网页中会出现一个可拖动的**悬浮球（彼方）**，点击后从页面中央弹出精美的前端面板，包含全部功能：

0. **🌗 白天/深色主题**：Header 右侧可一键切换，选择自动记忆，随全局变量保存。

1. **🪄 状态**：查看每个 NPC 的幕后状态卡（可展开）、可能偶遇标记、更新统计；一键手动更新/刷新/清空。**删除楼层 / 重roll自动回退**：状态快照存在楼层里、随楼层存亡——删除多少楼层就自动回到对应楼层之前的幕后状态（保留最近 10 次更新的快照，快照楼层全被删则清空）；重roll（重新生成最后一条回复）自动回到上一层状态；楼层内容被编辑时对应快照自动作废；切回旧 swipe 分支页会恢复该页当时的快照。**清空 = 真正回到空状态**：清空后会记录「清空层」，彼方只分析清空之后的新楼层，不再从旧楼层重新识别出之前的 NPC。
2. **⚙️ 设置**（每个选项都带有说明文字，此处为功能一览）：
   - **接口配置**：彼方使用**独立接口**更新幕后状态，与酒馆主生成接口互不影响。填写 OpenAI 兼容接口地址（末尾自动补 `/v1`）与 API 密钥，点击「获取模型列表」拉取模型后下拉选择；「测试连接」会发一条短消息验证可用性。**最大输出Token** 限制模型每次返回状态卡的最大长度（默认 60000，上限 131072，可参考模型页的最大输出长度；追踪 NPC 多或使用推理模型时建议调大），**温度**越低更新越稳定。**请求统一由酒馆服务器转发**（不再有浏览器跨域(CORS)问题，也不用再选直连还是转发；酒馆服务器需能访问该接口地址）。
   - **更新设置**：自动更新开关；**正文新角色自动建档**（默认开启——正文出现新角色自动建档追踪；关闭后只更新已追踪的 NPC，正文中出现的新角色一律不建档，需手动把名字加进追踪名单才会建档）；更新频率（每 N 条回复更新一次，1=每次都更新）；**读取最近 N 条 AI 回复**（默认 3，综合最近几条正文判断剧情与需要更新的 NPC；发送给接口的「最近正文回复」严格按这个数字取，**「最近剧情」上下文取同数量且不含正文的楼层**，不会重复也不会带入更早楼层）；**追踪当前角色卡角色**（默认关闭——仅群聊时角色卡名才是角色；若角色名只是卡片标题、角色写在世界书里，请保持关闭）；**写入世界书条目**（把幕后状态写入角色卡主世界书的常驻条目，蓝灯常开、禁递归，任何读取该世界书的环节都能读到；切换聊天时自动重新写入当前聊天的内容）；**给彼方接口注入世界书内容**（默认开启，读取角色卡绑定主+附加世界书与聊天世界书，不读全局世界书，按主 AI 的方式激活条目——蓝灯常驻、绿灯按关键字匹配最近回复——让更新 AI 理解世界设定与角色，可在日志页核对实际发送内容）；**常驻世界书条目**（每行一个条目名/关键词，命中的条目每次都强制注入、不走关键词激活——角色人设条目按关键词触发时正文没提到就读不到，用它保证人设始终可见）；**不再限制注入上限**（不按字数/条数截断，避免发给 AI 的世界书内容不完整）。
   - **标签过滤**：处理发给模型的回复内容。`排除` 模式移除指定标签内的内容；`只读` 模式只保留指定标签内的内容（没有这些标签的楼层保留原文）。**标签直接写名字即可**（如 `thinking`、`aftertalk`、`branches`，不用带尖括号，带 `<thinking>` 也会自动处理）；兼容带属性写法（如 `<aftertalk status="out_of_story">`）。另外 HTML 注释（`<!-- ... -->`，常见于模型思考块）始终会被清理，Subtext 思维链（`<!-- begin_of_Subtext_think -->…<!-- end_of_Subtext_think -->` 整块，含中间纯文本思考内容）也会一并删除；若回复里只有 `</标签>` 而没有开头的 `<标签>`（如模型只输出了 `</thinking>` 结尾的思维链），`排除` 模式会把楼层开头到该结尾标签的整段内容（含中间多段思考）一并删除。
    - **追踪NPC名单**：在**仪表盘的「追踪 NPC 管理」**中添加/删除本聊天要持续追踪的 NPC 名字，**随当前聊天保存，新聊天默认为空**；也可留空，由 AI 自动识别重要 NPC。
3. **🛡️ 事实档案**：查看每个 NPC 的**跨楼层记忆账本**——身份锚点/未完成承诺/近期关键事件。这些字段会发送给彼方更新 AI, 并在开启注入后提供给主 AI; 代码会自动追加/去重/保留最近三条, 防止"礼物从玩偶变零食"类的跨楼层不一致。
4. **📜 日志**：查看**本轮实际发送给彼方接口的完整内容**（系统指令 + 玩家输入(独立 system) + 最近剧情 + 最近正文回复 + 世界书条目 + 现有状态卡(含人设参考)，全部可展开查看与复制）与 AI 输出、使用的楼层、更新/移除的 NPC；**「复制报错内容发给助手」**会把完整报错报告（时间/模型/楼层/请求/输出）复制到剪贴板，方便直接粘贴给 AI 助手排查。

悬浮球可拖动到任意位置，位置会自动记忆。

接口兼容性: 任何支持 `GET /v1/models` 与 `POST /v1/chat/completions` (OpenAI 兼容) 的服务均可使用, 例如各类 OpenAI / DeepSeek / one-api / new-api 网关等。若地址不以 `/v1` 结尾会自动补上。

## 数据存储

- **设置**: 全局变量 (`global` 变量, 键 `彼方_settings`) —— 接口配置、更新选项、标签过滤等全局偏好。局域网访问同一酒馆服务器的设备共享同一份配置；导出酒馆助手脚本不会携带设置中的敏感信息（接口密钥等）。旧版本存在脚本变量里的设置会自动迁移并清空。
- **NPC 状态与监控名单**: 状态快照存在**当前聊天各楼层的楼层变量** (`message` 变量, 键 `彼方`) 里, 每次更新写入本次分析的最后一条楼层(快照随楼层存亡——删除楼层/重roll自动回退, 这是回滚能力的来源); 聊天变量 (`chat` 变量, 键 `彼方`) 只保留轻量索引(有快照的楼层列表 + 清空层)。切换到其他聊天/角色卡时名单与状态互不干扰, 默认从空开始。旧版本把状态本体存在聊天变量里的数据, 会在升级后首次访问该聊天时自动迁移为楼层快照(迁移成功才覆盖旧数据, 失败则保留待重试)。

## 2026-10-10 — 注入改成竖线表（表头只写一次 + 动态列集）

`buildInjectionPrompt` 交给主 AI 的那段，从「每个 NPC 一行、每行把字段名重写一遍」改成「表头 + 数据行」：字段名只在表头出现一次，每行按列对齐。

- **列是动态的**：只保留**本批至少有一个 NPC 有值**的列，全员皆空的列整个丢掉——所以没开生理监测的聊天看不到「生理周期 | 怀孕 | 周期影响 | 防护 | 性行为」，没有恋爱对象的聊天也看不到「好感 | 情欲 | 名分 | 标签 | 恋爱态度」。空值填 `—`（一个字符，换掉的是原来的 `标签: ` 前缀）。
- **恋爱拆成 5 列**，不再是 `恋爱: 好感 暧昧 · 情欲 想要 · 名分 恋人` 那样一条复合段——`好感 / 情欲 / 名分 / 标签 / 恋爱态度` 各占一格，和其余字段同一张表。
- **`未完成事项` 折成单行**：台账原本是多行文本，直接进表格会把一行撕成好几行；现在换行压成 `; `，末尾那句「事实提醒」仍在格内（口吻不变）。
- **零字段兜底照旧**：整批 NPC 一个字段都没有时，退回 `- 名字 | 状态未知`，不输出一行空表头。
- **不改提示词语义**：注入仍然只给阶段名/名分/标签/态度，不给 0–100 的裸数值；`情感倾向`、`恋爱动向`、`好感值`、`情欲值` 一律不进注入。
- **红线不受影响**：这段在 `buildInjectionPrompt` 里，不在 `buildUpdateMessages`。「没有标记任何 NPC ⇒ 更新提示词逐字节不变」的 192 组 byte-diff 打的是后者，二者是两个函数。注入侧的断言由 `tests/prompt-shape.test.ts`（表头首格是「名字」、恋爱五列落在表头末五位、裸数值不许出现）与 `tests/bifang-backstage-ledger.test.ts`（台账渲染落在「未完成事项」这一列的数据格里）钉住。

## 2026-10-10 — 恋爱子系统（标记即开关：不标记则提示词逐字节不变）

新增 `src/彼方_NPC幕后生命状态系统/恋爱规则.ts`（纯函数）+ `tests/bifang-love-rules.test.ts`，其余改动落在 13 个既有文件里（含 `数据变更.ts`：玩家手改 `恋爱标签` 也要过闭合词表）。设计口径见 `docs/彼方-恋爱子系统-策划案-v1.md`（v10）。

- **没有全局开关**：在 NPC 详情页点「标记恋爱对象」写 `恋爱对象=是`，取消标记写空值（空值即删除）。**没有任何 NPC 被标记时，提示词与从前逐字节相同**——恋爱说明段只做「任务 user 消息」的尾部追加，未标记时输出空串。这条由一次性 byte-diff（改 `prompts.ts` 的那一轮必须机械重跑：**192 组** = 64 组开关 × 3 变体，`JSON.stringify(messages)` 与基线 `1b9db1c` 比：未标记 **128/128 组逐字节相同、0 字节差异**；标记的 64 组剥掉那一段后逐字节相同、且那一段在 64 组里完全一致 = 恋爱说明段 **1323 字节**）+ `tests/prompt-shape.test.ts` 的常驻结构断言双重守住。
- **冷启动 / 开局（v10）**：人设写着「青梅竹马 / 未婚妻 / 已在一起多年」的 NPC，光标记会从 `好感 0 / 陌生` 起步（模型被禁止报数字，"既成关系"也不是本轮正文，单轮上限 +8 要爬 11 轮）。所以起点做成**第五样惰性补齐**：AI 在 `恋爱事件` 里额外加一条 `轴="开局"`，只报**阶段名**（`好感`/`情欲`/`名分` 可省，`依据` 必填、可来自人设），代码按**档下界**落值（恋人 86 / 有性趣 21）。两道闸：`恋爱开局 ≠ 是` 且 `恋爱动向` 为空（**防迟到乱开**）；开局是**基线不是增量**（不吃单轮上限），**只填缺省、绝不覆盖**手改值，同轮里 **`名分` 事件压过开局名分**；接受后写 `恋爱开局=是` 并留一行 `好感开局 86(人设：…)`，**没报就什么都不写**（窗口留着，漏报还能补）。
- **空轮不落库（v10 裁决 · 漏报不锁死的前提）**：数值状态类字段「**有值才写**」——`该轴有值 = 卡上非空 ∥ 本轮开局填了该轴 ∥ 本轮该轴有事件`（事件看**折算命中过没有**，不看净额：`+3` 与 `−3` 同轮相抵、净额 0 也照样落）。`名分` 没有伴生字段，闸更紧：**只在真的变了或本轮开局填了它时才写**（不每轮空转写回；玩家清空后不再被补成 `'无'`）；`情感倾向` / `恋爱基准日期` 是配置与锚点，照旧无条件惰性补齐。**没有这条，「漏报不锁死」是假的**：漏报那轮若先把 `好感值` 落成 `'0'`，下一轮的缺省闸就不成立 → 86 永远填不进去，而标记照写，窗口就此关死。代价（已知并接受）：第一次产生数据前详情页两条轴显示为**空**而不是 `0 / 陌生`。
- **AI 只报事实，代码算数值**：AI 只返回 `恋爱事件`（轴/类型/强度/依据），代码折算成两条轴：好感（存量，不衰减）与情欲（状态量，会被满足与时间回落）。代码持有阶段表、±2 滞回、情感倾向的 (敏感度, 粘性) 系数、单轮上限、情欲地板。
- **单轮上限只夹涨方向**（好感 +8 / 情欲 +20）：落方向不设限，一条「性行为(大)」情欲真的掉 −35 而不是被夹成 −20（用例钉住）。
- **系数怎么乘（v4）**：好感涨/落与情欲涨 × 敏感度；**情欲落（满足回落 + 时间回落）只 × 粘性，不乘敏感度**——否则"外放(1.4)"会变成"性爱之后冷却得更快"，语义正好反了。病娇的「性行为(大)」= −35 × 0.2 = −7。
- **情欲地板只截断回落、不抬升（v4）**：`实际回落 = min(原回落, max(0, 情欲 − 地板))`，地板按**结算后**的好感阶段取（刚确定关系的那一夜之后就按新关系冷却）。情欲低于地板时回落不生效，但也不会被拉到地板上——所以"深爱但清心寡欲"能存在，手改的情欲值也不会被凭空抬高（与验收标准"手改后不覆盖"一致）。
- **一份隐藏基准日期**：`恋爱基准日期` 存上一轮结算的剧情日期（照 `生理周期日期` 的先例，只前进不倒退），时间回落按真实天数差算；剧情时间缺失/非法时跳过回落且不更新基准——**没有依据就不动手**。
- **闸在复制之前**：`mergeCard` 末尾那整块恋爱代码以 `恋爱对象=是` 为闸，未标记的 NPC 连 `恋爱事件` 都**不复制入卡**（它不在 `CARD_FIELDS` 里，一旦入卡没有任何路径会删，会随快照膨胀），只 `console.warn` 一句；用例钉住"未标记的卡上不出现 `恋爱事件` 键"。
- **注入只给阶段名/名分/标签/态度，不给 0–100 的裸数值**：主 AI 需要的是"该怎么演"，不是分数。生成侧要求只写外在可观察的倾向；真机若仍在复述态度，从 `prompts.ts` 的 `buildInjectionPrompt` 摘掉那一段即可（字段仍在卡上，零数据损失）。
- **一致性**：名分变更必须走名分事件**并附原文依据**（缺依据整条拒绝，不做 `依据 || 类型` 兜底），`恋爱动向` 记一行因果供玩家核对；`恋爱标签` 走闭合词表（词表外的词丢弃、去重、上限 5），AI 路径与**玩家手改路径**都过同一个 `校验标签`，且"归一化后为空"不等于"想清空"（AI 报错 → 保留旧值；玩家清空输入框 → 删字段）；旧「恋爱对象表」数据一律不迁移，从零开始。

**验证**：`pnpm test` 45 个用例文件全绿（恋爱规则 222 条断言、prompt-shape 57 条、data-mutation 65 条）；`pnpm build` 成功。

## 2026-10-09 — 收纳坞改为「坞声明契约、插件只消费」

方向纠正（用户提问）：「为什么是别的插件去兼容收纳？不应该是收纳兼容别的插件嘛？」——这条成立，这轮把它翻过来。

**症状**：装了「悬浮球收纳」后，更新弹窗/弹条落在**球原来的位置**，与收纳条图标对不上；球原来那 40×40 还在**白吃点击**。

**根因**（实测）：坞把球**藏起来**是给球 iframe **里面的元素**打 `data-floating-dock-hidden`（`div.bf-orb`），**不是**给 iframe 本体打，也**从不搬走 iframe** —— iframe 仍停在原地、40×40、`pointer-events:auto`。

**为什么不让坞反过来搬 iframe**：iframe 是本插件自己建的，位置/尺寸由 `悬浮球界面.vue` 的 `applyFrame` 自己算（打开面板时罩满视口）；坞再搬一次就是两套布局打架。⇒ **搬 iframe 的活儿归插件，坞只交出「图标在哪」。**

  - 编辑楼层: 楼层内容 hash 与快照记录不一致时该快照自动作废(继续往前回退), 撤销编辑恢复原文后快照又生效;
  - 切回旧 swipe 分支页: 恢复该页写入时的快照(此前版本做不到)。
- **体积控制**: 写入新快照时物理删除更早楼层的超额快照(保留最近 10 份), 长聊天不会膨胀。
- **旧数据自动迁移**: 旧版存在聊天变量里的当前状态与最近 10 份历史快照, 按当时的 AI 楼层换算成楼层号逐份写入对应楼层; **全部写入成功才覆盖旧结构, 任一步失败保留旧数据下次重试**, 不会丢数据。
- **事件处理简化**: `MESSAGE_DELETED`/`MESSAGE_SWIPED` 现在只需刷新界面与世界书注入(状态本身已随楼层自动回退/恢复)。

## 2026-08-03 — v1.0 创建

- 依据《Elsewhere/彼方 设计初稿》实现核心工作流: 监听 AI 回复 → 检测不在场景中的 NPC → 用独立 API 更新其幕后状态卡并保存到聊天变量。
- NPC 状态卡: 当前在做 / 当前状态 / 接下来想做 / 当前目标 / 心里惦记 / 最近变化 / 未完成事项, 遵循"不强行变化、不制造大剧情、保持一致性、只记录必要信息"原则。
- 时间跳跃处理: 从正文回复中识别"几天后/几个月后/一年后"等, 只更新跳跃后的当前状态。
- 未来扩展方向全部实现: 秘密想法、隐藏目标、位置、可能偶遇、NPC 后台互动。
- 独立 OpenAI 兼容接口: 支持自定义接口地址/密钥, 通过 `GET /v1/models` 获取模型列表并下拉选择, `POST /v1/chat/completions` 生成更新; 内置超时、错误提示、连接测试。
- 设置面板 (Vue): 接口配置、更新设置、NPC 名单管理、NPC 状态卡查看/移除、后台互动记录、手动更新与清空数据。
- 可选功能: 把 NPC 幕后状态注入到主 AI 提示词 (注入前过滤秘密想法/隐藏目标); 自动追踪新 NPC; 更新频率控制。
- 脚本按钮: 「彼方·手动更新」。
